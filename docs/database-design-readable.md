# DB設計の共有用説明書

## 1. このDBは何のためにあるか

このDBは、相手の機嫌・感情分析アプリで扱う大事な業務データを保存する場所です。

認証は Supabase Auth に任せます。そのため、このアプリのDBではログイン用ユーザーやログインセッションを自前で保存しません。

保存する業務データは大きく分けて次の3つです。

- 相談相手の情報
- 相談内容
- AIの分析結果

このアプリでは、ユーザーが過去の相談履歴を見返せることが重要です。たとえば「前にも同じ友人について相談した」「この上司は普段から短文だった」といった情報を後から確認できます。

実装計画では、過去の相談や人物情報をAIに渡すことで、その人との関係性や過去の傾向を踏まえた、より文脈に合う分析ができるようにします。

## 2. 全体の考え方

このDBは、Supabase Authでログインしたユーザーが使うことを前提にしています。

この文書では、DBカラム名としては `user_id`、アプリ側の変数名としては `userId` と書きます。どちらも Supabase Auth の `auth.users.id`、つまり「ログイン中のユーザーを表すID」という意味です。

ユーザーごとにデータを分けるため、相談相手、相談内容、AI分析結果はすべて `auth.users.id` に紐づきます。他人の相談内容は見えません。

相談相手ごとに履歴を持てます。たとえば「友人A」に関する相談を何件も保存でき、「上司A」に関する相談とは分けて確認できます。

1回の相談に対して、AI分析結果を保存します。さらに、将来の再分析に備えて、分析結果は履歴として複数保存できる設計にしています。

最新の分析結果は、`version` が一番大きいものとして扱います。作成日時は表示や監査のために使いますが、どれが最新かを決める基準にはしません。

KIGEN404は、単に「相手が怒っているか」を当てるだけのアプリにはしません。過去の相談、相手ごとの傾向、AIがそう判断した根拠、相談後の振り返りをつなげて、人間関係の不安を整理できるアプリにします。

## 3. テーブル全体像

| テーブル名 | 何を保存するか | 例 |
| --- | --- | --- |
| Supabase Auth `auth.users` | アプリを使うユーザーの認証情報 | 山田さんのログインアカウント |
| persons | 相談相手 | 友人A、上司A、恋人など |
| analysis_cases | 1回分の相談内容 | 「返信が冷たく感じた」相談 |
| analysis_results | AIの分析結果 | 怒っている可能性、返信例など |

ざっくり言うと、Supabase Auth の `auth.users` は「誰のデータか」を分けるための親、`persons` は相談相手の保存場所、`analysis_cases` は相談内容の保存場所、`analysis_results` はAIの回答・分析結果の保存場所です。

## 4. KIGEN404の差別化方針とDBの関係

KIGEN404は、他のAIチャットや感情分析ツールと違い、相談履歴と根拠を積み上げて人間関係の不安を整理することを目指します。

| 差別化方針 | どういう意味か | 関係するDB・AI・UI |
| --- | --- | --- |
| 人物ごとの関係性メモリを作る | 相手ごとに過去相談、普段の返信傾向、関係性メモを持つ | `persons`, `analysis_cases`, `analysis_results`, 実装計画の `person_profiles` |
| いつもの傾向と今回の異常を分ける | 普段から短文なのか、今回だけ冷たいのかを分けて考える | `analysis_cases`, `analysis_results`, 実装計画の `person_profiles` |
| AIの結論ではなく判断根拠を見せる | 「怒っている可能性」だけでなく、そう見える理由や別解釈を見せる | `analysis_results.result_json`, 分析結果UI |
| 返信文生成よりも認知の偏りを整える | 短文や絵文字なしを悪く解釈しすぎていないか整理する | `analysis_results.result_json`, 実装計画の `analysis_feedbacks`, `user_pattern_summaries` |
| 人間関係のOSにする | 相談、分析、根拠確認、行動、振り返り、次回への反映をつなげる | `persons`, `analysis_cases`, `analysis_results`, 実装計画の `analysis_feedbacks`, `person_profiles`, `user_pattern_summaries` |

AIの分析結果は、絶対的な診断として扱いません。あくまで「この入力と過去履歴から見ると、こういう解釈があり得る」「悪く見すぎなくてよい理由もある」「次はこの行動が安全そう」という整理の材料として扱います。

ユーザー自身の不安傾向を扱う場合も、心理診断ではなく、利用履歴から見える傾向として扱います。

## 5. Supabase Auth

Supabase Auth は、アプリを使うユーザー本人の認証を担当します。

主に次の処理をSupabase Authに任せます。

- 新規登録
- ログイン
- ログアウト
- セッション管理
- パスワード管理
- refresh token管理

アプリ側では、認証済みユーザーのIDである `auth.users.id` を使って、相談相手・相談内容・分析結果を紐づけます。

## 6. 自前認証で作らないもの

Supabase Authを使うため、次のものはアプリ側では作りません。

- 自前 users テーブル
- auth_sessions テーブル
- password_hash カラム
- refresh_token_hash カラム
- refreshToken ローテーションSQL
- HMAC-SHA256によるrefreshToken保存
- bcrypt / Argon2idによる自前パスワード保存
- logout時の revoked_at 管理
- JWTの自前発行処理
- `/api/auth/register`
- `/api/auth/login`
- `/api/auth/refresh`
- `/api/auth/logout`

これらは、Supabase Authが担当する範囲です。

## 7. persons テーブル

`persons` は、相談対象の相手を保存するテーブルです。

たとえば次のような相手を保存します。

- 友人
- 上司
- 恋人
- 家族
- 同僚
- 顧客

相手の普段の特徴やメモも保存できます。たとえば「普段から短文」「忙しい時期は返信が遅い」といった補足です。

1人のユーザーは複数のPersonを持てます。Personごとに相談履歴を見られるため、「友人Aについての過去相談」「上司Aについての過去相談」を分けて扱えます。

Personを後から編集しても、過去相談の文脈は壊さない設計です。過去の相談には、その相談を作った時点の相手情報を別途保存します。

将来的には、Personごとに「普段の返信傾向」「相談履歴から見える特徴」「関係性メモ」を要約し、関係性メモリとして使えるようにします。

## 8. analysis_cases テーブル

`analysis_cases` は、1回分の相談内容を保存するテーブルです。

主に次の内容を保存します。

- 実際に起きたこと
- 自分が送った文
- 相手から返ってきた文
- 直前の会話
- 背景事情
- 自分の不安
- 分析状態

このテーブルを見ると、「過去にどんな相談をしたか」が分かります。

`status` で、その相談が未分析なのか、分析中なのか、分析済みなのか、失敗したのかを管理します。

`person_snapshot` には、相談を作った当時の相手情報を保存します。これにより、後からPersonのメモや関係性を編集しても、過去相談の文脈は変わりません。

`analyze_run_id` は、AI分析の実行を識別するためのIDです。古いAI実行が後から戻ってきても、現在の状態を壊さないようにするために使います。

ユーザーは自分の `analysis_cases` だけ見られます。他人の相談内容は見えません。

過去の相談履歴と組み合わせることで、「いつもの傾向」と「今回だけ違う可能性」を分けて整理できるようにします。

## 9. analysis_results テーブル

`analysis_results` は、AIが返した分析結果を保存するテーブルです。

主に次のような内容を保存します。

- 感情や状態のスコア
- AIがそう判断した理由
- 返信例
- 避けた方がよい表現
- 行動提案
- そう判断した根拠
- 悪く見すぎなくてよい理由
- 別の解釈

1つの相談に対して、複数の分析結果を持てます。たとえば将来、プロンプトやAIモデルを変えて再分析した場合も、前の結果を消さずに履歴として残せます。

最新結果は `version` が一番大きいものです。`created_at` は作成日時ですが、最新判定の基準ではありません。

AIの構造化出力全文は `result_json` に保存します。

`result_json` は、単なるスコアだけでなく、判断根拠、別解釈、避けるべき行動、次に取る安全な行動をUIに表示するための材料になります。

## 10. ユーザーが過去相談を見られる仕組み

ユーザーは、自分が作成した過去相談を見られます。

見られるものは次の通りです。

- 自分の相談ケース一覧
- 特定の相手に関する相談履歴
- 1つの相談の詳細
- 1つの相談に対する最新AI分析結果
- 必要に応じて過去の分析結果履歴

すべての取得処理では、必ず `user_id` で絞ります。この `user_id` は Supabase Auth の `auth.users.id` です。これにより、ログイン中のユーザー本人のデータだけを返します。

他人の `personId`, `caseId`, `resultId` を指定しても、APIは404を返します。403ではなく404にする理由は、そのデータが存在するかどうか自体を隠すためです。

## 11. 具体例

1. ユーザー「太郎」がSupabase Authでログインする。
2. 太郎のユーザーIDは Supabase Auth の `auth.users.id` として扱われる。
3. 太郎が `友人A` を `persons` に登録する。
4. 太郎が「友人Aから返信が冷たかった」という相談を作る。
5. その相談が `analysis_cases` に保存される。
6. AI分析結果が `analysis_results` に保存される。
7. 後日、太郎は友人Aの過去相談履歴を見られる。
8. ただし、別ユーザーの花子は太郎の相談内容を見られない。

この例では、太郎の `auth.users.id` で `persons`, `analysis_cases`, `analysis_results` が紐づいています。花子が太郎の相談IDを指定しても、APIは見つからないものとして扱います。

## 12. セキュリティ上の重要ポイント

- 認証は Supabase Auth に任せる。
- アプリ側DBにパスワードを保存しない。
- アプリ側DBにrefresh tokenを保存しない。
- 業務データをlocalStorageに保存しない。
- 相談本文や人物メモはDBに保存する。
- 取得時は必ず `userId` で絞る。この `userId` は Supabase Auth の `auth.users.id`。
- 他人のデータは404で隠す。
- ログに本文全文やAPIキーを出さない。
- 本番公開前はセキュリティ・個人情報・利用規約について専門家確認が必要。

このアプリでは、相談本文や人物メモがプライベートな情報になりやすいため、保存場所とアクセス制御を特に慎重に扱います。

### 運営者・開発者による閲覧について

相談本文、人物メモ、AI分析結果はDBに保存されるため、DB管理権限を持つ開発者・運営者は技術的には閲覧できる可能性があります。

ただし、通常運用ではユーザー本人以外が相談内容を閲覧しない方針にします。

運営者・開発者が相談内容を確認するのは、障害調査、問い合わせ対応、不正利用調査など、必要性がある場合に限定します。

また、ログには相談本文、人物メモ、AI分析結果全文を出力しません。

## 13. 差別化のための実装計画

KIGEN404を他のAIチャットと差別化するために、単にその場でAIに相談するだけでなく、過去の相談履歴をもとに、相手ごとの傾向やユーザー自身の不安パターンを整理できるようにします。

このため、以下の3つを実装計画に含めます。

- 分析結果へのフィードバック
- Personごとの傾向要約
- ユーザー自身の不安パターン要約

これらはファインチューニングやローカルLLMを前提にしたものではありません。

初期段階では、外部LLM APIに対して、DBに保存された相談履歴、人物ごとの傾向、ユーザーのフィードバックを必要な範囲で渡すことで実現します。

### 13-1. 分析結果へのフィードバック

AIの分析結果に対して、ユーザーが「役に立った」「少し違った」「実際にはこうだった」といったフィードバックを残せるようにします。

保存する例:

- 分析が役に立ったか
- 実際に相手との関係がどうなったか
- AIの見立てが合っていたか
- ユーザーによる補足や訂正

この機能により、AIの回答を出して終わりにせず、後から「どの分析が役に立ったか」「どのような場面でズレやすいか」を確認できます。

ただし、このフィードバックは最初からAIの学習データとして扱うものではありません。まずは、プロダクト改善、プロンプト改善、人物傾向の要約に使う参考情報として扱います。

### 13-2. Personごとの傾向要約

同じ相手について相談が増えてきたら、その相手の普段の傾向をまとめられるようにします。

保存する例:

- 普段から短文なのか
- 絵文字をあまり使わない人なのか
- 忙しい時期は返信が遅くなりやすいのか
- 過去にも同じような返信があったが問題なかったのか

これにより、AIは「一般的にこの返信が冷たいか」だけでなく、「この相手にしてはいつも通りなのか、いつもと違うのか」を判断しやすくなります。

また、毎回すべての過去相談本文をAIに渡すのではなく、必要な範囲で要約された傾向を渡すことで、コスト・速度・プライバシー面の負担を減らします。

### 13-3. ユーザー自身の不安パターン要約

相談履歴が増えてきたら、ユーザー自身がどのような場面で不安になりやすいかを整理できるようにします。

保存する例:

- 返信が短いと不安になりやすい
- 絵文字がないと冷たく感じやすい
- 既読後に時間が空くと悪い方向に考えやすい

ただし、これは心理診断ではありません。

「あなたは〇〇です」と決めつけるためではなく、アプリの利用履歴から見える傾向として、ユーザーが自分の考え方を整理するために使います。

### 13-4. 差別化方針と実装内容の対応

| 差別化方針 | 実装内容 |
| --- | --- |
| 人物ごとの関係性メモリ | `persons`、相談履歴、Personごとの傾向要約を使う |
| いつもの傾向と今回の異常を分ける | 過去の相談履歴と今回の相談内容を比較する |
| 判断根拠をUIで見せる | AIの結論だけでなく、理由・別解釈・注意点を表示する |
| ユーザーの認知の偏りを整える | フィードバックと不安パターン要約を使う |
| 人間関係のOSにする | 相談、分析、行動、振り返り、次回への反映をつなげる |

## 14. まとめ

- Supabase Auth の `auth.users` は誰のデータかを管理する。
- アプリ側では自前認証テーブルを作らない。
- `persons` は相談相手を管理する。
- `analysis_cases` は相談内容を管理する。
- `analysis_results` はAI分析結果と判断根拠を管理する。
- 過去相談はユーザー本人だけが見られる。
- 最新結果は `version DESC` で取得する。
- localStorageに相談内容は保存しない。
- KIGEN404は、相談履歴、根拠確認、振り返りを通じて人間関係の不安を整理するアプリとして発展させる。
