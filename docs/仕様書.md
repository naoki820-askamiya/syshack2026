# KIGEN404 現行仕様書

最終確認日: 2026-08-30

この文書は、現在のリポジトリに接続されている実装を基準にした仕様書です。将来構想や過去のMVP案は現行仕様として扱いません。

## 1. プロジェクト概要

KIGEN404は、人間関係で起きた出来事、相手の反応、自分の対応などを入力し、AIが状況の見方と次の行動を整理するWebアプリです。

AI出力は、相手の本心、感情、人格、病気などを事実として断定するものではありません。入力から考えられる複数の解釈、判断材料、安全な行動案を参考情報として表示します。

## 2. 現在の実装範囲

- Supabase Authによるメールアドレス登録、ログイン、ログアウト
- 分析対象となる人物の作成、一覧、詳細、更新、アーカイブ
- 人物ごとの相談作成、一覧、詳細
- OpenAI Responses APIによるAI分析
- 分析結果、根拠、不確実性、代替解釈、行動案、返信案の表示
- 分析結果へのFeedback作成、取得、更新
- パーソナライズ利用範囲の設定
- 保存済みPersonProfileと許可済み履歴・Feedbackの分析文脈への利用
- 保存済みUserPatternSummaryの取得、削除

PersonProfileとUserPatternSummaryを新規生成・更新するAPI、ゲスト分析API、同意記録APIは現在のルーターに実装されていません。

## 3. システム構成

| 層 | 主な責務 | 実装 |
| --- | --- | --- |
| ブラウザ | 入力、結果表示、Supabase Auth、API呼び出し | React、Vite、React Router |
| API | 認証、入力検証、所有権検証、状態遷移、AI実行 | Express、TypeScript |
| 認証 | ユーザー登録、ログイン、token検証 | Supabase Auth |
| DB | 人物、相談、分析結果、Feedback、設定等の保存 | PostgreSQL、Prisma |
| AI | 状況整理結果の生成 | OpenAI Responses API、Structured Outputs |

フロントエンドとバックエンドは別プロセスで動作します。Docker ComposeにもPostgreSQLやSupabaseサービスは含まれず、外部の接続先を使用します。

## 4. 認証・セッション仕様

### 4.1 認証の正本

認証の正本はSupabase Authです。アプリ独自の`users`、`auth_sessions`、JWT発行・検証処理は持ちません。

保護APIは次のヘッダーを要求します。

```http
Authorization: Bearer <Supabase access token>
```

バックエンドはtokenを独自に復号して認証済みとは判断せず、`supabase.auth.getUser(token)`で現在のユーザーを確認します。DBの所有者には、検証済みの`user.id`だけを使用します。リクエスト本文やクエリの`user_id`は所有者決定に使用しません。

### 4.2 ブラウザでのtoken保持

現在のSupabaseクライアントは`persistSession: false`、`autoRefreshToken: false`です。tokenをブラウザの永続ストレージへ保存しないため、ページ再読込やtoken期限切れ後に再ログインが必要になる場合があります。

相談本文やAI結果などの業務データも`localStorage`へ保存しません。画面遷移用キャッシュはメモリ内だけに置き、DBを正本とします。

### 4.3 `/api/me`

`GET /api/me`だけはtokenなしでも呼び出せます。

- tokenなし: `{ "user": null }`
- 有効なtokenあり: `{ "user": { "id": "...", "email": "..." } }`
- 無効なtokenあり: `401`

## 5. 所有権・データ保護

- Person、AnalysisCase、AnalysisResult、AnalysisFeedback等のDB検索・更新条件に認証済み`userId`を含めます。
- 他ユーザーのリソースと存在しないリソースは、どちらも`404 RESOURCE_NOT_FOUND`として扱います。
- 更新やアーカイブは、先に取得してから所有権を判定せず、更新条件自体に`userId`を含めます。
- PostgreSQLのRLSを有効にしますが、APIサーバー側の所有権条件も省略しません。
- CORSはOriginなしのサーバー間アクセスと、設定済みallowlistのOriginだけを許可します。
- OpenAI APIには`store: false`を指定します。

## 6. 主要データモデル

| モデル | 用途 | 主要な制約・関係 |
| --- | --- | --- |
| Person | 分析対象の人物 | `userId`所有、論理アーカイブ |
| AnalysisCase | 1件の相談と分析状態 | Personとの複合所有権、作成時Person snapshot |
| AnalysisResult | AI分析結果 | case単位の`version`、`analyzeRunId` |
| AnalysisFeedback | 結果へのFeedback | AnalysisResultごとに1件 |
| PersonProfile | 相手ごとの保存済み傾向 | user・person単位、refresh状態を保持 |
| UserPatternSummary | ユーザー全体の保存済み要約 | user単位 |
| UserPrivacySetting | パーソナライズ設定 | user単位 |
| UserConsentRecord | 同意記録用テーブル | 現行APIなし |
| GuestTrialAttempt | ゲスト試行管理用テーブル | 現行APIなし |
| ApiUsageEvent | AI利用量の予約・精算 | user、route、cost、statusを保持 |
| RateLimitPolicy | AI利用上限の運用設定 | route・subject・window単位 |

### 6.1 Person snapshot

AnalysisCase作成時に、Personの`displayName`と`relationshipType`をversion付きJSONとして保存します。後からPersonが更新されても、相談作成時の文脈で分析を再現するためです。

### 6.2 Prisma schemaとSQL migration

責務の正本は次のとおりです。

- Prisma schema: アプリが使用するモデル、列、relation、Prisma Client生成用の写像
- SQL migration: RLS、CHECK、trigger、partial index、DESC indexなどPostgreSQL固有の実体
- `auth.users`: Supabaseが管理する外部テーブル

Prisma schemaに表現されていないSQL固有設定を、不要と判断して削除してはいけません。適用済みmigration SQLを正として扱います。

## 7. AnalysisCaseの状態遷移

```text
draft  ── analyze開始 ──> analyzing ── 成功 ──> analyzed
failed ── analyze再実行 ─> analyzing ── 失敗 ──> failed
```

- `draft`と`failed`だけが分析を開始できます。
- `analyzing`への再実行は`409 CASE_ALREADY_ANALYZING`です。
- `analyzed`への再実行は`409 CASE_ALREADY_ANALYZED`です。
- 分析開始時に`analyze_run_id`を新規発行し、試行回数と開始時刻を更新します。
- 成功・失敗の更新条件にも開始時の`analyze_run_id`を含めます。古い非同期応答が新しい試行を上書きすることを防ぐためです。
- 成功時のcase更新とAnalysisResult作成は、同じSQLトランザクション内で実行します。
- 5分以上`analyzing`のcaseを`failed`へ戻すSQLは`prisma/operations/recover-stale-analyses.sql`にあります。実行スケジュール自体はリポジトリで定義していません。

## 8. AnalysisResultのversionと最新判定

- `version`はAnalysisCase内の論理順序です。
- 保存時は、そのcaseの既存`MAX(version) + 1`を採番します。
- 最新結果は必ず`version DESC`で判定します。
- `created_at DESC`へ置き換えてはいけません。
- 結果一覧も`version DESC`で返します。
- `(analysis_case_id, version)`と`(analysis_case_id, analyze_run_id)`は一意です。

## 9. API仕様

### 9.1 共通

- 既定のローカルURL: `http://127.0.0.1:3000`
- JSONリクエストは`Content-Type: application/json`
- 保護APIはSupabase Bearer tokenが必須
- UUID形式のpath parameterと入力本文はZodで検証
- 一覧の`limit`は1〜50、既定20、`offset`は0以上、既定0

成功時は各APIのデータをJSONで返します。共通エラー形式は次のとおりです。

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "入力内容を確認してください。",
    "status": 400,
    "requestId": "req_..."
  }
}
```

クライアント指定の`x-request-id`は100文字以内なら引き継ぎ、それ以外はサーバーで発行します。レスポンスヘッダーにも`x-request-id`を返します。

### 9.2 Person API

| Method | Path | 認証 | 用途 |
| --- | --- | --- | --- |
| `POST` | `/api/persons` | 必須 | Person作成 |
| `GET` | `/api/persons` | 必須 | Person一覧 |
| `GET` | `/api/persons/:personId` | 必須 | Person詳細 |
| `PATCH` | `/api/persons/:personId` | 必須 | Person更新 |
| `POST` | `/api/persons/:personId/archive` | 必須 | Personの論理アーカイブ |
| `GET` | `/api/persons/:personId/profile` | 必須 | 保存済みPersonProfile取得 |
| `GET` | `/api/persons/:personId/analysis-cases` | 必須 | 人物別AnalysisCase一覧 |

Person作成本文:

```json
{
  "displayName": "上司A",
  "relationshipType": "boss",
  "notes": "任意"
}
```

`relationshipType`は`boss`、`coworker`、`subordinate`、`lover`、`spouse`、`friend`、`family`、`customer`、`classmate`、`other`のいずれかです。`displayName`は1〜50文字、`notes`は任意で1〜1000文字です。未知フィールドは拒否します。

### 9.3 AnalysisCase API

| Method | Path | 認証 | 用途 |
| --- | --- | --- | --- |
| `POST` | `/api/analysis-cases` | 必須 | AnalysisCase作成 |
| `GET` | `/api/analysis-cases/:caseId` | 必須 | AnalysisCase詳細 |
| `POST` | `/api/analysis-cases/:caseId/analyze` | 必須 | AI分析実行 |
| `GET` | `/api/analysis-cases/:caseId/results/latest` | 必須 | 最新結果取得 |
| `GET` | `/api/analysis-cases/:caseId/results` | 必須 | version降順の結果一覧 |

AnalysisCase作成本文:

```json
{
  "personId": "00000000-0000-0000-0000-000000000000",
  "userAgeRange": "20代",
  "userGender": "回答しない",
  "perceivedPartnerReaction": "冷たい",
  "elapsedTimeType": "直後",
  "eventFacts": "資料を送った後、短い返信が来た",
  "userResponseType": "action",
  "userResponseText": "確認ありがとうございますと返信した"
}
```

`userResponseType`は`action`、`conversation`、`none`です。`none`の場合だけ`userResponseText`は`null`、それ以外は1〜3000文字の本文が必要です。Personが他ユーザー所有または存在しない場合は404です。

分析成功レスポンスの外形:

```json
{
  "status": "analyzed",
  "result": {
    "id": "...",
    "analysisCaseId": "...",
    "version": 1,
    "promptVersion": "kigen-prompt-v2",
    "resultSchemaVersion": "kigen-analysis-result-v2",
    "model": "...",
    "generatedAt": "...",
    "analysis": {}
  }
}
```

最新結果がまだない場合、`GET .../results/latest`は`{ "result": null }`を返します。

### 9.4 Feedback API

| Method | Path | 認証 | 用途 |
| --- | --- | --- | --- |
| `POST` | `/api/analysis-results/:resultId/feedback` | 必須 | Feedback作成 |
| `GET` | `/api/analysis-results/:resultId/feedback` | 必須 | Feedback取得 |
| `PATCH` | `/api/analysis-feedbacks/:feedbackId` | 必須 | Feedback更新 |

Feedback本文は次の任意フィールドを受け取ります。

- `actualOutcome`: 1〜50文字または`null`
- `helpfulnessScore`: 1〜5の整数または`null`
- `overreadScore`: 1〜5の整数または`null`
- `usedRecommendedAction`: booleanまたは`null`
- `outcomeNote`: 1〜1000文字または`null`
- `allowPersonalizationUse`: boolean

同じAnalysisResultへ2件目を作成すると`409 FEEDBACK_ALREADY_EXISTS`です。Feedback側とプライバシー設定側の両方で利用が許可されている場合だけ、対応するPersonProfileをrefresh対象にします。

### 9.5 プライバシー・要約API

| Method | Path | 認証 | 用途 |
| --- | --- | --- | --- |
| `GET` | `/api/privacy-settings` | 必須 | 設定取得。未作成なら既定値で作成 |
| `PATCH` | `/api/privacy-settings` | 必須 | 設定更新 |
| `GET` | `/api/user-pattern-summary` | 必須 | 保存済みUserPatternSummary取得 |
| `DELETE` | `/api/user-pattern-summary` | 必須 | 保存済みUserPatternSummary削除 |

設定項目は`personalizationEnabled`、`usePersonProfile`、`useUserPatternSummary`、`useFeedbackForContext`です。現行のAI文脈生成では`useUserPatternSummary`の設定値にかかわらずUserPatternSummaryをAIへ渡しません。

## 10. AI分析仕様

### 10.1 API呼び出し

- OpenAI Responses APIのStructured Outputsを使用します。
- `store: false`、SDKの`maxRetries: 0`です。
- アプリ内部では最大3回まで試行します。
- 1回の既定timeoutは30秒です。
- 明示的なrefusalと設定不足は再試行しません。
- incomplete、provider error、timeout、出力検証失敗は試行上限内で再試行します。

### 10.2 AIへ渡す情報

- AnalysisCase作成時のPerson snapshot
- 現在の相談入力
- 設定で許可されたPersonProfile
- 同じPersonの直近3件の分析済みcaseから、`version DESC`で選んだ最新結果の要約
- 利用許可済みの直近3件のFeedback

ユーザー入力は`untrustedUserInput`として渡し、入力内の命令文を実行しないよう指示します。UserPatternSummaryは現行実装では渡しません。

### 10.3 出力契約

主な出力は次のとおりです。

- `confidenceLevel`: `low`、`medium`、`high`
- 1行要約、文面の印象、状況からの読み取り
- 6つの0〜100整数スコア
- 心配材料、心配を弱める材料、不明点
- 代替解釈、考え方の偏り候補、バランスの取れた見方
- 推奨行動、避ける行動、最大3件の返信案
- 連絡タイミング
- 普段との比較
- 診断ではないことを示すdisclaimer

6指標のlabelとcategoryは固定です。

| key | label | category |
| --- | --- | --- |
| `anger` | 怒り気味 | concern |
| `coldness` | 冷たい | concern |
| `distance` | 距離あり | concern |
| `busyness` | 忙しい | context |
| `flatness` | 淡々 | context |
| `reassurance` | 大丈夫 | relief |

スコアは相手の本心の確率ではなく、入力から見える判断材料の相対的な強さです。

### 10.4 出力検証

- Zod Schemaに一致しない出力を拒否します。
- 診断、感情の断定、攻撃的行動、不安を煽る独自指標などの禁止表現を検出します。
- 一部の限定的な断定表現だけ、安全な可能性表現へ補正します。
- 高い懸念スコアには具体的理由とevidenceを要求します。
- 実際にAIへ渡していないPersonProfile、過去case、Feedbackを根拠として表示させません。
- 比較根拠が不足する場合は`usualVsCurrent`を無効化し、比較配列を空にします。

## 11. パーソナライズ仕様

- `personalizationEnabled`がfalseなら、現在の入力だけを分析に使います。
- `usePersonProfile`がtrueなら、同じuser・personの保存済みProfileを参照できます。
- 同じPersonの直近分析済みcaseは最大3件参照できます。
- `useFeedbackForContext`がtrueでも、Feedback自身の`allowPersonalizationUse`がtrueのものだけを最大3件参照します。
- 実際に使ったcase ID、Feedback ID、Profile IDとcontext snapshotをAnalysisResultへ保存します。
- 過去情報が存在しても比較根拠として十分でなければ、普段との比較を有効にしません。

## 12. Rate Limit・利用量管理

- `routeKey = analyze`、`subjectType = user`の有効なRateLimitPolicyを優先順で評価します。
- rolling windowとcalendar day windowを扱います。
- request数とcost unitの上限を扱います。
- 複数policyのadvisory lockを同じ順番で取得し、上限確認と予約を直列化します。
- 分析開始時に最大3試行分を予約し、完了後に実試行数へ精算します。
- 本番環境で有効なpolicyが0件の場合は`AI_CONFIG_MISSING`です。
- 利用量精算の失敗は分析結果を巻き戻さず、`usage_reconciliation_required`をログへ出します。

## 13. エラー方針

| HTTP status | 主な意味 |
| --- | --- |
| `400` | 入力・UUID・queryの検証失敗 |
| `401` | tokenなし、無効、期限切れ |
| `404` | 対象なし、または他ユーザー所有 |
| `409` | 状態競合、重複Feedback、古い分析応答 |
| `429` | AI利用上限超過 |
| `500` | 必須サーバー設定不足、内部エラー |
| `502` | AI providerまたはAI出力エラー |
| `504` | AI timeout |

内部例外や秘密情報はレスポンスへ含めません。利用者向けエラーとサーバーログは`requestId`で対応付けます。

## 14. 環境変数

主要な環境変数とセットアップ手順はREADMEを正とします。特に次の境界を維持します。

- `VITE_`付き変数へ秘密情報を入れない
- アプリ実行時のDB接続は`DATABASE_URL`
- Prisma CLIは`DIRECT_URL`を優先し、未設定時は`DATABASE_URL`
- AI分析には`OPENAI_API_KEY`と`OPENAI_ANALYSIS_MODEL`または`OPENAI_MODEL`が必要
- Supabase AuthにはURLと公開可能キーが必要

## 15. テストで固定する重要仕様

- Supabase Auth必須APIと認証済みuser IDの使用
- 他ユーザーのPerson、AnalysisCase、AnalysisResult、Feedbackを404として扱うこと
- クライアント指定`user_id`の拒否
- Person snapshotの保存
- AnalysisCaseの状態遷移と二重実行防止
- `analyze_run_id`が不一致の古い成功・失敗応答を保存しないこと
- AnalysisResultの原子的保存と`version DESC`による最新判定
- AI Structured Outputs、安全性、出典制限、最大試行数
- 旧形式分析結果の互換表示
- 業務データをWeb Storageへ永続化しないメモリ内キャッシュ
- 人物選択時に同じPersonの最新相談を利用すること

## 16. 現在の制約・未実装事項

- UserPatternSummaryは取得・削除のみで、生成処理はありません。
- PersonProfileの生成・refresh実行処理はありません。Feedback更新時は`needs_refresh`を立てるところまでです。
- stale AnalysisCase回復SQLの定期実行方法は未定義です。
- RateLimitPolicyの具体的な本番値はmigrationでseedしません。
- ゲスト試行、同意記録を操作するAPIはありません。
- Supabase sessionをブラウザへ永続化しないため、継続ログインは提供していません。
