# KIGEN404 現行仕様書

最終確認日: 2026-10-07

確認対象: ローカルの`develop`、`ed0f1c2`時点の実装

この文書は、現在の画面・API・データ処理を説明します。実装の確認に基づく仕様であり、本番環境への反映や動作検証の完了を示すものではありません。未実装・未決定事項は第17節にまとめています。

セットアップは[README](../README.md)、テーブル・制約の詳細は[DB設計書](database-design.md)を参照してください。[差別化機能の実装計画](differentiation-implementation-spec.md)には将来構想も含まれるため、現行動作はこの文書と実装を基準に確認します。

## 1. プロジェクト概要

KIGEN404は、人間関係で起きた出来事、相手の反応、自分の対応を入力し、AIが複数の見方と次に取れる行動を整理するWebアプリです。

AIの出力は、入力から考えられる解釈を示す参考情報です。相手の本心・感情・人格・病気を事実として断定せず、判断材料、別の解釈、不明点、安全な行動案を提示します。

### 1.1 主な利用の流れ

1. メールアドレスとパスワードで登録・ログインします。
2. 相談する相手を選ぶか、新しく入力します。
3. 出来事、相手の反応、自分の対応などを入力して相談を保存します。
4. 保存した相談をAIが分析し、結果・根拠・不確実性を表示します。
5. 行動案や返信例を確認し、後からFeedbackとして振り返りを保存できます。
6. 履歴から相談を再表示し、許可した過去情報を次回の分析に利用できます。

### 1.2 用語

| 用語 | この文書での意味 |
| --- | --- |
| Person | 相談の対象となる相手 |
| AnalysisCase（相談） | 出来事や反応などの入力と、分析の進行状態 |
| AnalysisResult（分析結果） | AI出力と、生成・参照情報の記録 |
| Feedback（振り返り） | 分析への評価や、その後の出来事についての本人の報告 |
| Person snapshot | 相談作成時に保存する相手の名前・関係性の写し |
| PersonProfile | 相手ごとの保存済み要約。生成・再生成処理は未実装 |
| UserPatternSummary | ユーザー全体の保存済み要約。生成・AI利用は未実装 |

## 2. 現在の実装範囲

画面で利用できる主な機能は次のとおりです。

- Supabase Authによる登録・ログイン・ログアウト
- 相手の情報を使った相談作成と、保存済みの相手の名前・関係性の編集
- AI分析の開始、保存済み相談からの状態確認・再試行
- 分析結果、根拠、不確実性、別の解釈、行動案、返信例の表示
- 相談履歴の表示と人物による絞り込み
- Feedbackの作成・取得・更新と、次回分析への利用許可・撤回
- パーソナライズに使う情報の設定

APIには、人物の一覧・詳細・更新・アーカイブ、人物別の相談一覧、保存済みPersonProfileの取得、保存済みUserPatternSummaryの取得・削除もあります。APIの存在が、それぞれの専用画面の提供を意味するわけではありません。

PersonProfileとUserPatternSummaryを生成・更新するAPI、ゲスト分析API、同意記録APIは実装されていません。

## 3. 画面・操作仕様

### 3.1 画面とURL

| 画面 | URL | ログイン | 主な用途 |
| --- | --- | --- | --- |
| ホーム | `/` | 閲覧は不要 | 相談作成への入口。ログイン中は最近の相談対象・履歴を表示 |
| 登録 | `/register`、`/signup` | 不要 | メールアドレス・パスワードで登録 |
| ログイン | `/login` | 不要 | 認証後、指定された戻り先へ移動 |
| 新しい相談 | `/new` | 必須 | 相手・出来事・反応・対応の入力と保存 |
| 分析結果 | `/analysis/:id` | 必須 | 保存済み相談の分析状態・結果の表示 |
| 行動提案 | `/action/:id` | 必須 | 行動案、避ける行動、返信例の表示 |
| 相談履歴 | `/history` | 必須 | 相談一覧と人物による絞り込み |
| プライバシー設定 | `/privacy-settings` | 必須 | 過去情報を分析に使う範囲の設定 |

互換URLとして、`/dashboard`はホーム、`/persons`と`/persons/:personId`は履歴、`/analysis-cases/:caseId`は分析結果を表示します。`/settings`は未提供であることを案内する画面です。

未ログインで保護画面を開くと、ログイン画面へ移動します。登録時のメール確認の有無はSupabase環境の設定に従い、確認が必要な場合はメールを確認してからログインするよう案内します。パスワード再設定は未提供です。

### 3.2 ホーム・相談履歴

ホームには、相談履歴からまとめた最近の相談対象と、作成日時が新しい順の相談を最大5件表示します。人物を選ぶと、その人物の履歴へ移動できます。

相談履歴は作成日時の降順で表示します。絞り込みは人物IDを基準とし、`/history?personId=...`や`/persons/:personId`からも指定できます。人物ボタンは長い名前を折り返して表示し、選択状態を`aria-pressed`で伝えます。

読込中・取得失敗・履歴なしを区別して表示します。取得に失敗した場合は再取得でき、再取得時も人物の絞り込みを維持します。カードから保存済み相談の分析画面を開けます。

### 3.3 新しい相談

入力は同じフォーム内の2区分で整理します。必須項目には印を付け、未入力や入力エラーを表示します。

| 区分 | 入力内容 |
| --- | --- |
| 1. 相手と出来事 | ニックネーム、関係性、自分の年代・性別、起きた出来事 |
| 2. 反応と自分の対応 | 相手の反応、経過時間、自分の対応 |

自分の対応は、行動の自由記述、会話の入力、何もしていない、から選びます。会話入力には自分・相手の発言を追加する形式と、会話をまとめて入力する形式があります。

過去に相談した相手の候補は、同じ人物の最新相談を基準に表示します。相手を選んだ後は保存済みPersonを取得し、名前・関係性を確認できます。「相手の情報を編集」から明示的に保存すると、そのPersonを更新します。通常の名前入力で別の名前に変えた場合は、以前の人物IDを引き継ぎません。

送信時は、必要に応じてPersonを作成し、その後に相談を保存します。相談の保存が確認できたら分析画面へ移動し、AI分析を開始します。送信中、人物情報の読込中・取得失敗時、人物編集中は相談の送信を抑止します。

### 3.4 分析状態・結果

新規相談から移動した場合は分析を開始します。履歴やURLから開いた場合は、保存済み結果と相談状態を確認します。メモリ内のキャッシュがない場合はAPIから表示データを取得します。

結果がまだない場合は、保存済み相談の状態と、状態の再取得・同じ相談での分析や再試行の操作を表示します。`analyzing`では分析を重複送信せず、2秒間隔で状態を確認します。自動確認は開始から120秒以内の範囲で行い、その後は手動で再取得できます。分析要求の通信に失敗した場合も、最新結果と状態を照合してから再送の可否を判断します。

結果画面の上部に、1行要約、相手の名前・関係性、分析の確信度を表示します。確信度はAI自身の評価であり、実測した正解率や相手の感情を認定する値ではないことを説明します。旧形式で確信度がない場合は「記録なし」と表示します。

その下に、6指標のスコア、文面の印象、状況からの読み取り、連絡のタイミング、根拠と不確実性、別の見方、普段との比較、Feedback、注意書きを表示します。根拠は「気になるサイン」「心配を弱めるサイン」「まだ分からないこと」に分け、出典と根拠の強さを表示します。

今回の入力、各スコアの理由、ほかの解釈、比較の詳細は折りたたみで確認できます。折りたたみは標準の`details`・`summary`を使い、キーボードで開閉できます。要約の近くから、行動・返信例、根拠、振り返りへ移動できます。

旧形式の分析結果は互換表示します。現行APIでは、分析済み相談への分析の再実行は受け付けません。

### 3.5 行動提案・Feedback

行動提案画面には、推奨行動、避ける行動、返信例とその注意点を表示します。返信例はクリップボードへコピーできます。

Feedbackでは、役に立った度合い、読みすぎだと感じた度合い、最大1000文字の振り返り、次回分析への利用許可を保存できます。2つの評価は1〜5で、両端の意味を表示します。選択済みの数字をもう一度押すと未選択へ戻ります。

保存済みFeedbackを取得してから、作成と更新を選び分けます。取得・保存に失敗した場合は再取得して保存状態を確認します。既存Feedbackは後から編集でき、利用許可をOFFにして保存すると次回分析への利用を撤回できます。Feedbackは本人の報告であり、AI出力の正解ラベルとして扱いません。

### 3.6 プライバシー設定・読みやすさ

プライバシー設定では、過去情報全体の利用、相手ごとのProfileの利用、許可済みFeedbackの利用を切り替えます。全体をOFFにすると下位の操作を無効にします。変更は「設定を保存」で確定し、取得失敗時は再取得できます。保存要求には4つの設定フラグだけを含め、取得応答のIDや日時などは送信しません。

設定をOFFにしても保存済みデータは削除しません。自分全体の傾向要約は現在の分析に利用しないことを、画面上でも案内します。

相談入力・分析結果・行動提案・履歴・プライバシー設定には共通の読みやすさ調整を適用します。本文・補足文字の大きさ、行間、長文の折り返し、リンクとボタンのフォーカス表示を整えています。折りたたみの見出しとFeedbackの評価・保存ボタンには、高さ48px以上の操作領域を設けています。

### 3.7 履歴取得・キャッシュ

ホームと履歴では、Person一覧と人物ごとの相談一覧をページ単位で取得します。人物別の相談取得は、1回の読込につき最大4並列です。

各読込にAbortControllerと30秒の総期限を設け、最初の取得失敗、画面を離れたとき、認証状態の切り替わり、期限切れで未完了の取得を取り消します。全件が成功し、開始時と同じ認証状態である場合にだけ、メモリ内キャッシュを置き換えます。

この30秒はクライアントの復帰用の期限であり、実測したSLAではありません。通常のGETや、同じユーザーによるほかの並列API呼び出しを一律に直列化するものでもありません。検証記録は[履歴取得・認証修正の統合記録](overnight-review/astra-remediation-summary.md)を参照してください。

## 5. 認証・セッション

### 5.1 認証と所有者の決定

認証の正本はSupabase Authです。アプリ独自の`users`・`auth_sessions`や、JWTの発行・検証処理は持ちません。保護APIには次のヘッダーが必要です。

```http
Authorization: Bearer <Supabase access token>
```

バックエンドは`supabase.auth.getUser(token)`で現在のユーザーを確認します。DBの所有者には検証済みの`user.id`を使い、リクエスト本文やクエリのユーザーIDを採用しません。

認証情報がない場合や無効な場合は401です。認証基盤の通信障害、SDK APIの5xx、予期しないSDK例外は、機密情報を含まない500として扱います。通信障害を「認証情報が無効」と判断して401へ変換しません。

### 5.2 ブラウザでの保持

Supabaseクライアントは`persistSession: false`、`autoRefreshToken: false`です。トークンをブラウザの永続ストレージに保存せず、自動更新もしないため、ページ再読込や期限切れ後に再ログインが必要になる場合があります。

相談本文・分析結果などの業務データも`localStorage`・`sessionStorage`へ保存しません。画面遷移用のキャッシュはメモリ内に置き、DBを正本とします。認証状態の切り替わりでキャッシュを消去し、以前の認証状態で開始した取得結果が新しいキャッシュへ混入しないよう確認します。

### 5.3 `/api/me`

`GET /api/me`は、ログイン状態を確認するAPIです。

| リクエストの状態 | 応答 |
| --- | --- |
| Authorizationヘッダーなし | `{ "user": null }` |
| 有効なトークンあり | `{ "user": { "id": "...", "email": "..." } }`。emailは`null`の場合あり |
| 無効な認証情報あり | `401 AUTH_INVALID` |
| 認証基盤の通信障害・SDK例外 | 機密情報を含まない`500` |

`GET /health`も認証不要で、`{ "status": "ok" }`を返します。サーバーの起動確認用であり、DB接続やAI分析の成功を保証しません。

## 6. 所有権・データ保護

Person、相談、分析結果、Feedbackなどへのアクセスは、認証済み`userId`で所有権を確認します。他ユーザーのリソースと存在しないリソースは、どちらも`404 RESOURCE_NOT_FOUND`として扱います。

Personの更新・アーカイブや分析の状態更新は、更新条件自体に所有者を含めます。Feedback更新は、所有者を条件に取得したレコードのIDを使って更新します。

SQL migrationにはPostgreSQLのRLSを有効にする定義があります。API側でも所有権を検証し、DB側の制御に依存して省略しません。接続先DBへの適用状況は別途確認が必要です。

CORSは、Originなしのサーバー間アクセスと、許可リストに含まれるOriginを受け付けます。OpenAI APIには`store: false`を指定します。

### 7.1 主要モデル

| AnalysisFeedback | 結果への振り返り | AnalysisResultごとに1件 |
| PersonProfile | 相手ごとの保存済み要約 | ユーザー・人物単位、再生成が必要かを保持 |
| UserPatternSummary | ユーザー全体の保存済み要約 | ユーザー単位 |
| UserPrivacySetting | パーソナライズ設定 | ユーザー単位 |
| UserConsentRecord | 同意記録用テーブル | 操作するAPIは未実装 |
| GuestTrialAttempt | ゲスト試行管理用テーブル | 操作するAPIは未実装 |
| ApiUsageEvent | AI利用枠の予約・精算 | 所有者、元の相談・分析試行、利用量・状態を保持 |
| RateLimitPolicy | AI利用上限の運用設定 | ルート・対象・集計期間単位 |

### 7.2 人物情報とsnapshot

相談作成時に、Personの`displayName`と`relationshipType`をバージョン付きJSONとして保存します。後からPersonを編集しても、分析には相談作成時の名前・関係性を使います。

snapshotの取得と相談の作成は、同じ短いトランザクションで行います。所有中・未アーカイブのPersonを共有行ロックして読み取ります。人物の編集・アーカイブが先に確定した場合は更新後の情報を使うか404となり、読取後に競合した編集は相談保存後まで待機します。

人物の名前・関係性を編集した場合は、Personの更新と既存PersonProfileの再生成対象化を同じトランザクションで行います。現在のパーソナライズ設定がOFFでも、古いProfileをそのまま再利用しないよう対象化します。編集の競合は後から確定した更新を採用する既存方式を維持し、リビジョンによる競合検出は追加していません。

保存済み相談・結果のsnapshotは、人物の編集・アーカイブで書き換えません。一方、履歴の名前・関係性には最新のPerson情報を表示します。

### 7.3 作成要求の再試行と重複防止

PersonとAnalysisCaseのPOSTは、任意のUUID `createIntentKey`を受け付けます。

| 条件 | 動作 |
| --- | --- |
| 同じユーザー・同じリソース種別・同じキーで、正規化後の入力も同じ | 既存リソースを返す |
| 同じユーザー・同じリソース種別・同じキーで、入力が異なる | `409 CREATE_INTENT_CONFLICT` |
| キーなし | 通常どおり新規作成する |

キーとサーバー生成の入力識別値（fingerprint）は、リソースと原子的に保存します。通常のAPI応答やログには含めず、PATCHで変更できません。

Personの同一要求を再送した場合は、編集後の現在のPersonを返します。相談の再送では、元のsnapshot・分析試行・結果を保持し、分析や利用枠の予約を開始しません。参照Personがアーカイブ済み・不在の場合は404となり、復活させません。

重複防止情報の寿命はリソースに従い、削除後の再送は保証対象外です。画面内で保存結果を確認できていない同一要求には同じキーを再利用します。再読込をまたぐ未確認要求の回復は未実装です。

### 7.4 Prisma schemaとSQL migration

| 正本 | 責務 |
| --- | --- |
| Prisma schema | モデル、列、リレーション、Prisma Client生成用の写像 |
| SQL migration | RLS、CHECK、トリガー、部分インデックス、降順インデックスなどのDB定義 |
| Supabaseの`auth.users` | 認証基盤が管理するユーザー |

Prisma schemaに表現されていないPostgreSQL固有の設定も、SQL migrationで管理します。schemaにないことを理由に削除せず、適用済みmigrationを確認します。

## 8. 分析の状態遷移・同時実行

### 8.1 開始・成功・失敗

```text
draft / failed ── 分析開始 ──> analyzing
                                ├── 成功 ──> analyzed
                                └── 失敗 ──> failed
```

- 分析を開始できる状態は`draft`と`failed`です。
- `analyzing`への開始要求は`409 CASE_ALREADY_ANALYZING`です。
- `analyzed`への開始要求は`409 CASE_ALREADY_ANALYZED`です。
- 開始時に`analyze_run_id`を新規発行し、試行回数と開始時刻を更新します。
- 成功・失敗の更新条件にも、その試行の`analyze_run_id`を含めます。古い非同期応答が新しい試行を上書きしないためです。
- 成功時の相談状態更新とAnalysisResult作成は、同じSQLトランザクションで実行します。

### 8.2 長時間続く分析の回復

`workflow.repository.ts`には、指定時刻より古い`analyzing`を検出・回復するヘルパーがあります。回復時は所有者・分析試行ID・状態・開始時刻を照合し、未来の時刻を基準にした回復を拒否します。

このヘルパーはAPIや定期実行に接続していません。`src/backend/prisma/operations/recover-stale-analyses.sql`には5分の条件がありますが、本番の回復基準として採用した値ではありません。定期実行方法、本番の基準時間、回復に伴う未精算利用枠の扱いは未決定です。

## 9. 分析結果のバージョン・最新判定

`version`は、同じ相談内での結果の論理順序です。保存時に既存の`MAX(version) + 1`を採番します。

最新結果は`version DESC`で判定し、結果一覧も同じ順序で返します。生成日時の降順へ置き換えません。DBでは`(analysis_case_id, version)`と`(analysis_case_id, analyze_run_id)`をそれぞれ一意にします。

## 10. API仕様

### 10.1 共通ルール

- ローカルの既定URLは`http://127.0.0.1:3000`です。
- JSONリクエストには`Content-Type: application/json`を指定します。
- 業務APIはSupabase Bearerトークンが必須です。例外は前述の`/api/me`と`/health`です。
- パス内のIDはUUID形式、本文・クエリはZodで検証します。
- 一覧の`limit`は1〜50（既定20）、`offset`は0以上（既定0）です。
- JSON本文の受付上限は`100kb`です。AIへ送る情報量の上限とは別に検証します。

成功時は、各APIのデータをJSONで返します。共通エラー形式は次のとおりです。

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "入力内容を確認してください。",
    "status": 400,
    "requestId": "req_..."
  }
}
```

クライアント指定の`x-request-id`は100文字以内なら引き継ぎ、それ以外はサーバーで発行します。レスポンスヘッダーにも`x-request-id`を返します。

## 11. AI分析仕様

### 11.1 呼び出し・再試行

OpenAI Responses APIのStructured Outputsを使用します。`store: false`、SDKの`maxRetries: 0`を指定し、再試行はアプリ側で管理します。

| 項目 | 現行値・動作 |
| --- | --- |
| 内部試行回数 | 最大3回 |
| `max_output_tokens` | 各試行32,768 |
| 既定タイムアウト | 全試行と再試行前の待機を含めて合計30秒 |
| 不完全な出力（incomplete） | 成功結果として保存しない |
| 再試行前の待機 | 250ms・500msを基準に`Retry-After`を尊重 |

ネットワークエラー、HTTP 408/429/500/502/503/504、不完全な出力、出力検証失敗は、最大試行回数と総期限の範囲で再試行します。明示的な拒否（refusal）、設定不足、入力不正、中断・キャンセル、再試行対象以外の恒久的な4xx、その他のproviderエラー・未知の例外は再試行しません。

各試行には総期限までの残り時間を渡し、新しいAbortControllerを使います。待機もキャンセルでき、待機によって総期限を超える場合は再試行しません。この30秒はAI処理の既定値であり、認証・DB保存・画面表示まで含む全体のSLAではありません。

### 11.2 AIへ渡す情報と上限

常に渡す情報は、相談作成時のPerson snapshotと現在の相談入力です。設定と利用条件が許す場合に、次の情報を追加します。

- 同じユーザー・同じ人物の保存済みPersonProfile
- 同じ人物の直近3件までの分析済み相談から選んだ、最新結果の1行要約
- 同じ人物に関する、個別に利用許可された直近3件までのFeedback

過去相談は`lastAnalyzedAt`の降順で選び、各相談内では`version DESC`の最新結果を参照します。1行要約は最大500文字です。Feedbackは作成日時の降順で選び、ID、実際の結果、読みすぎ評価、振り返り、出典情報を渡します。役に立った度合い・推奨行動の実行有無は、現在のAI入力には含めません。

ユーザー入力は`untrustedUserInput`として渡し、入力内の命令文を実行しないよう指示します。UserPatternSummaryは渡しません。

| 対象 | 上限 |
| --- | --- |
| PersonProfile | UTF-8 JSONで64KiB、コンテナの深さ16 |
| AI入力JSON全体 | UTF-8で128KiB |

複製・JSON変換とprovider送信前に検査し、超過時は切り詰めず`422 AI_INPUT_LIMIT_EXCEEDED`を返します。循環参照、JSONで表現できない値、実行可能なJSON変換フックも拒否します。これらは情報量の上限であり、API料金を保証する値ではありません。

### 11.3 出力契約

出力は`kigen-analysis-result-v2`のSchemaに従います。主な内容は次のとおりです。

- 確信度`confidenceLevel`（`low`、`medium`、`high`）と1行要約
- 文面の印象、状況からの読み取り、6つの0〜100整数スコア
- 心配材料、心配を弱める材料、不明点
- 代替解釈、考え方の偏り候補、バランスの取れた見方
- 推奨行動、避ける行動、最大3件の返信案と注意点
- 連絡タイミング、普段との比較、診断ではないことを示す注意書き

6指標のキー・ラベル・分類は固定です。

| key | label | category |
| --- | --- | --- |
| `anger` | 怒り気味 | `concern` |
| `coldness` | 冷たい | `concern` |
| `distance` | 距離あり | `concern` |
| `busyness` | 忙しい | `context` |
| `flatness` | 淡々 | `context` |
| `reassurance` | 大丈夫 | `relief` |

スコアは、入力から見える判断材料の相対的な強さです。相手の本心の確率として扱いません。

### 11.4 出力検証

- Schemaに一致しない出力を拒否します。
- 診断、感情の断定、攻撃的な直接指示、不安を煽る独自指標など、実装された禁止表現を検出します。
- 避ける行動の名称や完全な否定文など、限定した文脈に限って例外を認めます。
- 一部の限定的な断定表現を、安全な可能性表現へ補正します。
- 高い懸念スコアには、具体的な理由と根拠を要求します。
- 渡していないPersonProfile、過去相談、Feedbackを出典として使う出力を拒否します。
- 比較根拠が足りない場合は`usualVsCurrent`を無効化し、比較配列を空にします。

表現検査は、既知の問題に対応する実装です。あらゆる表現・言語に対する安全性や、解釈の正しさを保証するものではありません。

## 12. パーソナライズ仕様

### 12.1 設定と参照範囲

`personalizationEnabled`がOFFなら、相談作成時のPerson snapshotと今回の入力だけを使います。ONの場合は同じ人物の過去要約を最大3件参照し、個別設定に応じてProfileとFeedbackを追加します。過去相談だけをOFFにする独立した設定はありません。

Feedbackは、`useFeedbackForContext`とFeedback自身の`allowPersonalizationUse`が両方ONの場合だけ参照します。設定の変更・許可撤回は、次回の分析文脈の構築に反映します。過去の分析結果や保存済みの参照記録を書き換える処理ではありません。

### 12.2 PersonProfileの利用条件

`usePersonProfile`がONでも、保存済みProfileを無条件に渡すわけではありません。同じユーザー・人物に属し、次の条件を満たすものを参照します。

- `needsRefresh`がfalseで、`staleSince`が未設定
- 生成モデル名・Schemaバージョン・有効な生成日時が記録されている
- 元の相談IDと、1件以上の相談またはFeedbackの件数が記録されている
- 元の相談が同じユーザー・人物に属することを確認できる

条件を満たさないProfileは除外します。Profileの存在や件数だけで、要約の内容が正確であると認定しません。Profileの生成・再生成は未実装です。

### 12.3 参照情報の保存と表示

実際に参照した相談ID・Feedback ID・Profile IDと、出典情報を含む文脈のsnapshotをAnalysisResultへ保存します。現在の入力・本人のFeedback・過去のAI要約を区別し、過去のAI出力を事実へ格上げしません。

過去情報があっても、比較根拠が十分でなければ普段との比較を無効にします。UserPatternSummaryは設定や保存済みデータがあっても参照しません。

## 13. 利用上限・利用量管理

### 13.1 上限確認と予約

`routeKey = analyze`、`subjectType = user`の有効なRateLimitPolicyを優先順に評価します。直近の一定期間（rolling window）と暦日単位（calendar day）で、要求数と利用単位の上限を扱います。

複数のpolicyに対するアドバイザリロックを同じ順番で取得し、上限確認と予約を直列化します。分析開始時には最大3試行分を予約します。`costUnits`は試行数に基づく利用枠であり、providerの請求額ではありません。

新しい予約には認証済み所有者・元の相談・DBが生成した分析試行IDを記録し、相談の開始更新と同じトランザクションで保存します。本番環境で有効なpolicyが0件の場合は`AI_CONFIG_MISSING`です。具体的な本番値はmigrationで初期登録しません。

### 13.2 精算と未確定の利用量

完了後は既知の実試行数で精算します。所有者・利用イベント・元の相談と試行ID・予約状態`allowed`を照合し、精算済みの再送、不一致、対象なしを区別します。現在の試行IDが変わっていても、元の予約を照合して精算できます。

外部呼び出し開始後に実試行数が不明な場合は、予約を0へ変換せず保持します。旧記録・ゲスト記録のNULL紐づけを時刻から推測して補完したり、所有者削除後の記録を推測で精算したりしません。

利用量の精算に失敗しても分析結果を巻き戻さず、`usage_reconciliation_required`をログへ出します。状態回復に失敗した場合は`analysis_compensation_required`を記録します。

## 14. エラー・計測方針

| HTTP status | 主な意味 |
| --- | --- |
| `400` | 入力・UUID・クエリの検証失敗、不正JSON（`INVALID_JSON`） |
| `401` | 認証情報なし・無効・期限切れ |
| `404` | 対象なし、または他ユーザー所有 |
| `409` | 分析状態・作成要求の競合、重複Feedback、古い分析応答 |
| `413` | JSON本文の受付上限超過（`PAYLOAD_TOO_LARGE`） |
| `422` | AI入力の情報量超過・参照情報の形式不正 |
| `429` | AI利用上限超過 |
| `500` | 必須設定不足、認証基盤障害、内部エラー |
| `502` | AI provider・AI出力のエラー |
| `504` | AIタイムアウト |

内部例外や秘密情報は応答へ含めず、エラー応答に`requestId`を付けます。分析処理では、相談・試行ID、処理段階ごとの時間、件数、試行数、利用量などを記録し、相談本文やAI出力全文を計測ログへ含めません。

ブラウザ側にも、相談送信から保存結果の表示までの時間を記録する処理があります。計測処理の実装や個別の検証記録を、本番の処理時間・品質・利用者への効果の保証として扱いません。
