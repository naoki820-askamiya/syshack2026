# 規約・プライバシーポリシーの公開準備

確認日: 2026-10-07。利用者向け本文は[src/app/legal/documents.ts](../src/app/legal/documents.ts)です。この資料は運用の提案であり、実施済みの運用や法令適合の確認済み証明ではありません。

## 今回作成したもの

- 未ログインでも読める`/terms`と`/privacy-policy`。
- ホーム・登録画面・相談送信前からのリンク。入力を保つため、リンクは別タブで開く。
- 登録送信前の説明と未選択の同意チェック。「同意して登録する」の操作で登録する。
- 登録直後に認証済みセッションがある場合は、その場で文書の版とサーバー日時を本人の同意記録へ保存する。記録だけが失敗した場合は同意記録だけを再試行する。
- メール確認が必要な登録と、未記録・文書更新後の既存ユーザーには、認証後の`/consent`で改めて明示同意を取得する。
- 現行版の記録がない場合は、新しい相談の保存・分析APIを403で止める。既存履歴の閲覧とプライバシー設定は引き続き使える。

文書版は`2026-10-07-draft-2`と本文内容の識別子を組み合わせています。規約・ポリシーのどちらか一方でも版が変われば、既存ユーザーも再同意が必要です。過去の同意記録は残し、新しい版の記録を追加します。

更新時は本文と[共有版定義](../src/shared/legal.ts)の該当SHA-256を一緒に更新します。本文・見出し・ドラフト案内の変更と識別子が一致しない場合、回帰テストが失敗します。識別子を更新すると、公開版のラベルを据え置いた場合でも同意判定の版が変わります。正式版への移行時はラベルも更新し、ドラフトの記録を流用しません。

今回の実装にDB migrationは含めません。既存の`user_consent_records`を使用しますが、本番での適用状態は別途確認が必要です。

## 運用の推奨案

### 運営者

個人運営なら実際に責任を負う個人、法人運営なら法人を明記します。プロジェクト名やGitHubのアカウント名だけで代用しません。チーム開発の場合も、対応責任者とデータ管理権限を持つ人を決めます。

公開する氏名・名称、住所、法人の場合の代表者などの範囲は、運営形態と適用法令を確認して確定します。リポジトリの作者情報から運営者を推測して載せることは避けます。

### 問い合わせ・削除依頼

最初は専用の非公開メール窓口を1つ用意する案を推奨します。担当者が確認でき、個人的な連絡と分けられることが重要です。独自ドメインがあれば専用アドレス、なければ管理できる専用メールアカウントを用意します。公開IssueやSNSのコメント欄は、相談データの窓口にしません。

削除依頼は、登録メールからの連絡またはログイン済み画面での申請を使い、アカウントの所有者を確認します。パスワードや身分証の画像は通常の依頼で求めません。相談本文の再送も原則不要とし、対象IDまたは「全相談」「退会」で対象を指定できる設計にします。

受付確認・完了までの目標日数は、対応担当と作業手順を決めて実行可能性を確認してから公表します。未整備の窓口や達成できない期限を本文に記載しません。

### 保存期間

相談履歴を見返すことが主機能なので、一律30日削除は適しません。通常は本人が履歴として保持している間に保管し、相談単位の削除と退会時の削除を提供する案を推奨します。永久保存を既定の約束にはしません。

長期未利用データの整理は次の段階です。「最終利用から12か月で事前通知し、30日間反応がなければ整理」は検討候補ですが、法律上の一律期限ではなく、本サービス向けの仮案です。利用実態、通知可能性、復帰時の不利益、バックアップからの復元手順を確認して採否を決めます。この期限を今回のポリシーやコードには採用していません。

現在は相談・結果・Feedbackの自動削除と利用者自身の削除画面がありません。正式公開までに最低限、非公開窓口と実行可能な削除手順を用意し、対象・残るデータ・期限を説明する必要があります。

### 削除の範囲

本人の相談だけを対象にし、相談・分析結果・Feedbackに加えて、派生要約や参照記録に内容が残る可能性を調べます。退会では人物、設定、同意記録、利用量記録と認証アカウントの扱いも確認します。外部キーのCASCADEだけで、すべての履歴・派生情報・ログが消えるとは判断しません。

バックアップ、障害・不正利用の記録、外部サービスの保持は、本体DBの削除と分けて期限・目的を説明します。復元時に削除済みデータを再び有効にしない手順も必要です。削除操作・通知・本番DB変更は今回の作業には含めていません。

## 正式公開までに確定する項目

| 項目 | 現状 | 完了条件 |
| --- | --- | --- |
| 運営者情報 | 未決定 | 責任を負う主体と必要な公開情報を確定 |

| 海外への送信 | 契約・地域による扱い未確認 | 委託・第三者提供等の分類と、必要な情報提供・同意を確認 |

| 正式版の同意 | ドラフトの確認のみ | 本文と共有版を更新し、必要な同意を再取得。提示した旧版は版管理で保管 |

## 根拠と確認範囲

入力画面の送信前に利用目的を示す構成は、個人情報保護委員会の通則編3-3-4を参考にしました。運営主体・請求手続・苦情窓口などの確認は3-8・3-9を参照します。適用の判断は実際の運営形態に合わせて確認します。[個人情報保護委員会のガイドライン](https://www.ppc.go.jp/personalinfo/legal/guidelines_tsusoku/)

OpenAIのAPIデータは既定では学習対象に使われず、不正利用監視ログは通常最大30日保持されます。例外や契約・設定の違いがあります。`store: false`だけで外部保持がゼロになるとは案内しません。[OpenAI公式のデータ管理説明](https://developers.openai.com/api/docs/guides/your-data)

認証サービスの説明は[Supabaseのポリシー](https://supabase.com/privacy)も参照できます。これはKIGEN404自身の責任・窓口・実環境の設定の説明を代替しません。

過去の実装調査は[保存・削除監査](overnight-review/data-retention-delete-audit.md)を参照してください。同意APIの未実装という過去時点の記述は、今回の変更後には当てはまりません。
